# 约5分钟的代码与软件展示脚本

## 0:00—0:40 说明环境

“这里是设备状态监测的合成工业环境：一台电机、一套循环泵背景设备，后端使用Linux、Windows与VxWorks节点画像。采集、预处理、检测和告警有不同平台版本。界面容量条表示资源预留。”

指出顶部“合成环境 / Java + CloudSim”，不要说已经部署了真实三系统容器或RTP。

## 0:40—1:20 展示算法与方案

指出四个服务所在节点、备用节点、CPU/RAM预留，以及CloudSim传输/启动/就绪事件。
打开本轮project中的ScenarioLoader、CompatibilityChecker、BeamSearchPlanner和PlanRuntime，说明配置→兼容检查→规划→部署事件的代码路径，不逐行朗读全部代码。

## 1:20—2:50 注入节点故障并恢复业务

选择当前采集服务所在节点离线。观察该节点变为离线，并由兼容备用节点接管服务；资源不足时业务仍阻断。
点击诊断，区分NODE_OFFLINE和UPSTREAM_UNAVAILABLE。接管事件只包含迁移服务。再执行修复，原节点恢复在线备用，服务保留在接管节点，健康节点不重复启动。
展示目标节点恢复上线、驱动/运行环境恢复，最后验证业务链。节点统一显示在线；再次对同一节点注入故障，证明它可反复参与测试。

## 2:50—4:00 展示工艺故障

上一轮恢复验证通过后直接切换到电机过热并注入，也可按需重置。温度越过80°C，服务可以仍然正常部署。诊断为工艺温升，执行模拟冷却，推进采样，连续正常后验证。
指出工艺异常与部署异常的处理方法不同：前者冷却和观察，后者约束检查与重新部署。

## 4:00—5:00 展示验证证据与边界

展示已完成故障类型与累计轮次，再导出包含多轮诊断和迁移的演练记录；打开配置校验报告，展示100项检查和精确反例：更多服务不一定带来更多完整业务链。
说明当前精确解只覆盖固定拓扑/FIFO次序下的小规模接纳与放置；后续再进行真实平台及更广场景验证。

演示前检查：仅保留一个页面；浏览器最大化/F11；服务终端保持开启；准备从正常状态开始；无需联网。出现问题可先保存记录再重置，不必现场修改原Java源码。

 
## 备用接管与修复不回迁（当前规则）

平台故障注入后，自动迁出该节点全部服务，优先使用相同平台的空闲兼容备用节点；其它健康节点的部署固定。接管使用独立的64状态束搜索策略，检查累计CPU/RAM、平台能力和依赖，未声明全局最优。所选四种算法用于初始部署，接管不再全局重跑所选算法。

默认beam_search演示：vx-01承载collect/preprocess/alert。向vx-01注入驱动缺失，三个服务转移至vx-02，detect仍留在linux-01。点击诊断、修复、验证后，vx-01显示在线，CPU/RAM预留为0，标记备用节点；服务继续留在vx-02。随后可向vx-02注入故障，由已修复的vx-01接管。修复vx-02后，它也在线备用。无需重置，亦没有已隔离状态。

诊断保留注入时原部署的直接原因与依赖影响，同时说明接管后的当前可用性。CloudSim只对迁移／新启动的服务产生部署事件，保留节点不重复启动。工艺过热仍只启动模拟冷却，不迁移服务。

若备用资源或兼容条件不足，保留未接纳／阻断记录；节点自身修复后仍不得宣告全部业务恢复，可检查配置或选择重置。当前不自动回迁，也不自动借原节点重新补齐失败的接管。正常在线的备用节点与已修复节点仍可再次注入故障。
